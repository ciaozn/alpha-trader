## 1. 背景与目标

构建一个基于事件驱动架构的加密货币量化交易系统，覆盖「实时行情接入 → 多策略信号生成 → 风险控制 → 实盘自动执行」全闭环，交易标的为 Binance / OKX 的 U 本位永续合约。

**核心目标**：同一套策略代码可零改动地运行于回测、模拟盘、实盘三种模式，确保"回测验证有效的行为"与"实盘实际发生的行为"一致。

**核心用户**：系统运营者（开发者本人，兼具策略开发者角色）。

## 2. 用户场景与验收

场景按优先级排序；每个场景的验收条件必须可独立测试。

### 场景 1（P0）回测验证策略

运营者想在投入真金白银前，用历史数据验证 MA 交叉 / RSI 策略的表现。

- **Given** 本地已有 BTCUSDT 1h 近三年历史 K 线数据
- **When** 运营者以 BACKTEST 模式启动系统并指定策略与参数
- **Then** 系统回放全部历史数据，输出完整绩效报告：净值曲线、年化收益、夏普比率、最大回撤、胜率、盈亏比、逐笔成交明细
- **And** 同一输入重复运行 3 次，结果完全一致（确定性）

### 场景 2（P0）模拟盘全链路

运营者想在零资金风险下验证「信号 → 风控 → 下单 → 成交 → 持仓更新」全链路在真实交易所环境中的行为。

- **Given** 已配置 Binance testnet 的 API Key
- **When** 以 PAPER 模式启动系统并启用 MA 交叉策略
- **Then** 系统实时接收 testnet 行情，策略产生信号后自动完成下单、成交回报处理、持仓与净值更新
- **And** 每笔信号、订单、成交均可在数据库中查询，且收到告警推送

### 场景 3（P0）风控硬闸门

运营者要求任何订单在到达交易所前必须通过风控检查，超限信号必须被拦截。

- **Given** 风控规则已配置（杠杆上限、单笔限额、日亏损熔断等）
- **When** 策略产生一个超出限额的信号（如单日亏损已达熔断阈值后仍发出开仓信号）
- **Then** 该订单在风控层被拦截，不发往交易所，产生风控告警事件并推送通知
- **And** 拦截记录可查询，包含命中的规则与当时账户状态

### 场景 4（P1）断线自愈与对账

实盘运行中网络中断或交易所推送丢失，系统必须能自动恢复并保持状态正确。

- **Given** 系统在 PAPER/LIVE 模式运行中且持有仓位
- **When** WebSocket 连接中断 60 秒后恢复
- **Then** 系统自动重连并重订阅，随后执行一次全量对账（挂单 + 持仓），以交易所数据为准修正本地状态
- **And** 如发现本地无记录的"幽灵仓位"，按配置执行告警或自动平仓

### 场景 5（P1）实盘自动执行

运营者以小额资金开启实盘自动交易。

- **Given** 已完成 testnet 连续 7 天无异常运行，且实盘 API Key 已禁用提币并绑定 IP 白名单
- **When** 以 LIVE 模式启动系统
- **Then** 系统按与模拟盘完全相同的事件链路执行真实交易
- **And** 运行期间的信号序列与同期回测/模拟盘的信号序列一致（无行为漂移）

### 场景 6（P2）新增策略不改引擎

策略开发者想增加一个新策略（如布林带突破）。

- **Given** 系统已上线运行
- **When** 开发者实现策略 SPI 接口并在配置文件中启用
- **Then** 新策略接入全部链路（回测/模拟/实盘），事件引擎、风控、OMS 代码零改动

### 场景 7（P2）双交易所运行

- **Given** OKX 网关已实现
- **When** 配置同一策略同时交易 Binance 与 OKX 的同一标的
- **Then** 两个交易所的行情、下单、持仓在统一的内部模型下并行工作，互不干扰

## 3. 功能需求

> 编号规则：FR-<子系统>-<序号>。子系统：GW 行情网关 / EN 事件引擎 / ST 策略 / RK 风控 / EX 执行 / BT 回测 / OP 运行与监控 / SEC 安全。

### 3.1 行情网关（GW）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-GW-01 | 通过 WebSocket 订阅指定交易对的 K 线数据（Binance USDⓈ-M 永续），推送标准化行情事件 | P0 |
| FR-GW-02 | 连接中断后自动重连（指数退避），重连后自动恢复全部订阅 | P0 |
| FR-GW-03 | 启动时拉取并缓存合约交易规则（最小价格变动、最小数量步长、最小名义价值），下单前自动做精度对齐 | P0 |
| FR-GW-04 | 内部统一交易对表示（如 `BTCUSDT.PERP`），屏蔽交易所命名差异 | P0 |
| FR-GW-05 | 支持 Binance testnet 与实盘环境，仅由配置区分 | P0 |
| FR-GW-06 | 支持 OKX SWAP 永续（行情 + 交易 + demo 环境） | P1 |

### 3.2 事件引擎（EN）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-EN-01 | 单线程事件循环：事件按序处理，同一事件触发的连锁事件在本轮内闭环 | P0 |
| FR-EN-02 | 全部事件以 append-only 方式落盘（事件日志），含全局单调序号与业务时间戳 | P0 |
| FR-EN-03 | 时钟抽象：实盘使用系统时钟，回测使用随数据推进的虚拟时钟，组件不得直接读取系统时间 | P0 |
| FR-EN-04 | 支持定时器事件（用于对账、心跳等周期任务） | P0 |
| FR-EN-05 | 崩溃恢复：重启后可基于事件日志回放恢复系统状态 | P1 |

### 3.3 策略（ST）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-ST-01 | 提供策略 SPI：策略实现统一接口，通过配置启停和注入参数，新增策略不改动引擎代码 | P0 |
| FR-ST-02 | 内置双均线交叉策略：金叉做多、死叉平多/翻空，快慢线周期与是否允许做空可配置 | P0 |
| FR-ST-03 | 内置 RSI 超买超卖策略：周期、超买/超卖阈值可配置 | P0 |
| FR-ST-04 | 提供指标库：SMA、EMA、RSI、ATR，回测与实盘使用同一实现 | P0 |
| FR-ST-05 | 策略的唯一输出是信号事件；策略不得直接下单、不得读取时钟以外的系统状态 | P0 |
| FR-ST-06 | 策略可接收成交回报事件（onFill），用于策略内部状态管理 | P1 |

### 3.4 风控（RK）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-RK-01 | 风控是信号到订单之间的唯一通道，规则以管道串联，任一规则拒绝即拦截 | P0 |
| FR-RK-02 | 账户级规则：总杠杆上限、保证金率下限 | P0 |
| FR-RK-03 | 订单级规则：单笔名义价值上限、价格偏离最新价上限 | P0 |
| FR-RK-04 | 组合级规则：总持仓名义上限、单交易对持仓上限 | P0 |
| FR-RK-05 | 熔断规则：单日亏损达阈值禁止当日开仓；连续亏损 N 笔暂停交易 M 小时 | P0 |
| FR-RK-06 | 频率规则：单位时间最大订单数 | P1 |
| FR-RK-07 | 仓位换算：将信号意图换算为目标数量（按权益与目标敞口计算，并对数量步长取整） | P0 |
| FR-RK-08 | 拦截时产生风控告警事件并推送通知，拦截记录可查询 | P0 |
| FR-RK-09 | 规则参数外部化配置，支持不重启热更新 | P1 |

### 3.5 执行与订单管理（EX）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-EX-01 | 订单状态机：NEW → SUBMITTED → PARTIALLY_FILLED → FILLED / CANCELED / REJECTED，每次迁移落库 | P0 |
| FR-EX-02 | 每笔订单携带全局幂等键（clientOrderId），防止重复下单 | P0 |
| FR-EX-03 | 成交回报优先走 WebSocket 私有流，REST 查询兜底 | P0 |
| FR-EX-04 | 定时对账（默认 60s）：拉取交易所挂单与持仓，以交易所为准修正本地状态，差异触发告警 | P0 |
| FR-EX-05 | 幽灵仓位处理：发现本地无记录的实际持仓时，按配置执行告警或自动平仓 | P1 |
| FR-EX-06 | 成交后更新持仓与账户净值，并持久化 | P0 |

### 3.6 回测（BT）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-BT-01 | 历史数据回放：从本地存储读取历史 K 线，按时间顺序驱动完整事件链路 | P0 |
| FR-BT-02 | 模拟撮合采用保守规则：信号在 K 线收盘产生，下一根 K 线开盘价成交 | P0 |
| FR-BT-03 | 撮合计入滑点（可配置基点）与手续费（默认 taker 0.05%）与资金费率 | P0 |
| FR-BT-04 | 输出绩效报告：净值曲线、年化、夏普、最大回撤、胜率、盈亏比、逐笔成交明细 | P0 |
| FR-BT-05 | 提供历史数据下载工具：从交易所 REST 批量拉取 K 线并落库 | P0 |
| FR-BT-06 | 回测与实盘共享策略、风控、OMS 代码，仅行情来源、撮合器、时钟三处不同 | P0 |

### 3.7 运行模式与监控（OP）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-OP-01 | 支持 BACKTEST / PAPER / LIVE 三种运行模式，由配置切换，核心代码零改动 | P0 |
| FR-OP-02 | 提供 REST 状态接口：当前持仓、账户权益、引擎心跳、各网关连接状态 | P1 |
| FR-OP-03 | 告警推送（QQ 邮箱 SMTP → ciaozn@qq.com）：成交通知、风控拦截、熔断触发、断线重连、对账异常；异步发送 + 同类聚合节流 | P1 |
| FR-OP-04 | 持久化四类业务数据：订单、成交、信号、净值快照 | P0 |

### 3.8 安全（SEC）

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-SEC-01 | API 密钥通过环境变量注入，代码库与配置仓库中不得出现任何密钥 | P0 |
| FR-SEC-02 | 实盘 API Key 必须禁用提币权限并绑定 IP 白名单（部署检查项） | P0 |
| FR-SEC-03 | 风控参数热更新接口需要二次确认 | P2 |

## 4. 非功能需求

| 编号 | 需求 | 目标值 |
|---|---|---|
| NFR-01 | 事件处理延迟 | 单事件在引擎内的处理 < 100ms（不含网络 IO） |
| NFR-02 | 并发标的 | 单实例支持 ≥ 10 个交易对同时订阅与交易 |
| NFR-03 | 可用性 | 7×24 连续运行；断线自动恢复无需人工干预；testnet 连续运行 7 天为验收门槛 |
| NFR-04 | 确定性 | 相同回测输入重复运行，结果逐位一致 |
| NFR-05 | 可审计性 | 任意历史时刻的系统行为可通过事件日志完整回放 |
| NFR-06 | 可扩展性 | 新增策略、新增交易所均不改动事件引擎代码 |

## 5. 关键实体（数据视角）

| 实体 | 说明 | 关键属性 |
|---|---|---|
| Event | 一切驱动的载体 | 全局序号、业务时间戳、类型 |
| Kline | 标准化 K 线 | 交易对、周期、开高低收量、是否收盘 |
| Signal | 策略意图 | 策略 ID、交易对、方向（LONG/SHORT/FLAT）、强度、理由 |
| Order | 订单 | 幂等键、交易对、方向、类型、数量、价格、状态机状态 |
| Fill | 成交 | 订单号、价格、数量、手续费 |
| Position | 持仓 | 交易对、方向、数量、开仓均价、浮动盈亏 |
| Account | 账户 | 权益、可用保证金、保证金率 |
| RiskRule | 风控规则 | 层级、参数、是否启用 |

## 6. 边界情况

实现与测试必须覆盖以下情况：

1. **WS 推送重复或乱序**：同一根 K 线重复推送不得导致重复信号；乱序事件需有处理策略（丢弃过期或告警）
2. **下单成功但回报丢失**：对账机制必须能在下一轮周期内发现并修正订单状态
3. **K 线数据缺口**：回测数据缺根时不得静默跳过，需记录并计入报告
4. **数量精度边界**：仓位换算结果小于交易所最小数量时，放弃下单并告警（不得发脏单）
5. **资金费结算时点持仓**：回测与实盘都需按规则计提资金费
6. **交易所维护窗口**：REST 报错时需区分"拒单"与"交易所不可用"，后者重试而非判定失败
7. **系统重启时持仓**：重启后先从交易所全量同步持仓再恢复策略运行
8. **时钟漂移**：与交易所服务器时间偏差超过阈值时告警并暂停下单

## 7. 成功标准（可度量）

| 编号 | 标准 | 度量方式 |
|---|---|---|
| SC-01 | 回测性能 | BTCUSDT 1h 近三年数据，完整回测 + 报告生成 < 5 分钟 |
| SC-02 | 确定性 | 同一回测输入运行 3 次，绩效指标逐位一致 |
| SC-03 | 模拟盘稳定性 | testnet 连续运行 7 天，无未处理异常，对账零差异 |
| SC-04 | 风控有效性 | 覆盖全部五级规则的拦截测试用例，拦截率 100% |
| SC-05 | 同构一致性 | 同一时间段内，实盘/模拟盘产生的信号序列与回测回放一致 |
| SC-06 | 实盘审慎上线 | 实盘初始资金 ≤ 1000 USDT，观察 2 周无对账异常后方可加仓 |

## 8. 范围外（Out of Scope）

以下内容**明确不属于**本项目 v1：

- Tick 级 / 高频交易策略（K 线级别足够，引擎预留升级空间）
- 期权、现货杠杆、跟单交易
- Web 图形化仪表盘（v1 仅 REST 接口 + 告警推送）
- 机器学习 / AI 策略
- 多账户、多用户管理
- 策略参数自动寻优（网格搜索等，可作为后续迭代）

## 9. 假设与依赖

1. 实盘部署环境为可直连交易所 API 的海外 VPS（东京或新加坡）
2. 运营者持有 Binance（及后续 OKX）账户，可自行开通 testnet 与实盘 API Key
3. 运行环境提供 Java 21 LTS
4. 单实例、单账户架构（多账户是范围外）
5. 历史 K 线数据来源为交易所公开 REST 接口
